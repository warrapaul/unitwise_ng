Backend changes, in order
1. One acceptance shares the profile and documents (yes, this needs the backend)

addExistingUserAsTenant only creates the profile request when requestDocuments is true. Make it always create it.
respondToTenancyInvitation (PATCH /tenants/my/{id}/accept) only changes the status. It never approves the pending request, so the tenant has to accept twice.
Change: when accepting, approve that tenancy's pending profile+documents request in the same transaction. If the renter profile has no legal name or national ID, refuse the whole acceptance with a clear message rather than accepting half of it. The UI can then send them to finish their profile first.
Approving already moves the tenancy to PENDING and copies identity, so the change is only to call it from accept.
2. Tell the agency when the tenant answers

Accepting or declining an invitation publishes nothing today.
Add an event whose listener notifies the building's admins, for example "Jane Doe accepted the tenancy for A2, ld2 bl1". Use the same pattern as TenantProfileGrantListener.onGrantDecided.
3. Create a tenant from a share code

Redeeming a code today needs a tenancy that already exists, so a landlord can't start from a code.
Add POST /v1/tenants/{agencyId}/{buildingId}/from-share-code taking { shareCode, intendedRoomId, monthlyRent?, notes? }. In one transaction it should:
redeem the code (binding an open code to this agency);
create the tenancy for the code's owner, already PENDING, since the code is their consent;
copy their identity onto it and link the grant.
Guard it with TENANT_CREATE plus TENANT_DOCUMENT_READ. Keep the same single "invalid code" answer for wrong, expired and already-used codes.
4. Read the shared profile for one tenant

The tenant detail page downloads the agency's first 100 grants and filters them in the browser to find this tenant's profile. That breaks past 100 grants and goes against skills.md §28.12.
Add a tenantId filter to GET /profile-grants/{agencyId}, or a /tenant/{tenantId} route. The review-and-confirm step for the landlord (question 2 below) depends on this.
5. Show rooms by name

The "Room: #id" comes from the tenant /full response. It copies intendedRoomId but not intendedRoomName or intendedRoomNumber, so an unassigned tenant falls back to the ID. Copy those two fields.
The same response fills intendedRoomMonthlyRent and deposit from the room alone. Switch them to RoomTermsResolver, so they reflect agency → building → room like billing does.
6. Filter overdue payments by tenant

OverduePortfolioFilter already has agencyId, buildingId and search, so scoping to the context works now.
A tenant picker needs a tenantId filter; add it (and roomId if you want a room picker too).
Recommended, not blocking: 7. Show the agency's values on the building's contract settings

Blank building values fall back to the agency's, but the building response doesn't say what those are. A building-level admin may not be able to read agency settings to find out.
Return the effective values, or the agency's values alongside, so the building form can show "Using agency's: Jane Landlord" instead of a bare blank.
Your questions
1. Does "Accept" need backend changes? Yes, change 1. Adding the room name to the invitation doesn't: the data already includes it.

2. When does the landlord's record fill in from the shared profile?

Today: it fills in automatically the moment the tenant approves, but only fields that are still blank on the tenancy. Nobody confirms it.
Proposal: keep that pre-fill. On tenant detail, a "From their renter profile" panel shows the shared values next to the tenancy's, highlighting where they differ. It has "Use these details", which saves them through the existing landlord update, and "Edit".
Verification stays the actual confirmation, since it records who checked the details against the documents. This needs change 4, and no other new endpoint.
3. Where does a landlord enter a tenant's share code? A "Start from a share code" option on the add-tenant page, next to "Add by user ID". It needs change 3.

4. Renter profile drafts: no backend change. The backend only requires the legal name and ID when the status is COMPLETE; the UI always sends COMPLETE. The UI can save after any section, sending DRAFT until the identity fields are filled.

5. Contract details: agency or building?

Set them once per agency. Each building only fills in what differs, such as a different landlord, its own paybill, or its LR number. A landlord with ten buildings configures once, not ten times.
The premises name is the building's name and the town comes from its address, so neither needs setting anywhere.
Editing a room's or tenant's contract directly: I'd advise against editing the generated document. It's versioned, and it's what the tenant signs; hand edits can't be re-rendered when a value changes, and they break the link between a signature and a version. The per-lease pieces already exist without variables:
rent, deposit, due day and dates on the lease itself;
"Special terms" for free text;
a room-level template override for wording specific to one room.
