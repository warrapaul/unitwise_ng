DEPOSIT_MONTHS
It's a contract template variable: the deposit written as months of rent. The master tenancy agreement (clause 4.1) said "a deposit of {amount}, equivalent to {months} month(s)' rent". It's only filled in when the deposit divides into whole months, and it counted as required. So 100 on a rent of 1,000 blocked generation.

V31 removes that phrase from the master, so contracts state the amount only.
Custom templates copied from the old master: the variable now falls back to "—" instead of blocking.
Notifications
Every domain event now goes through NotificationDispatcher, and the admin's channel policy decides where each one goes. This covers:

sharing requests, decisions and share codes;
invitations and invitation answers;
room applications;
maintenance requests.
Before this, most of these were push-only and never reached the inbox, so they couldn't show in the list or the unread count.

Inbox: in-app delivery stores the notification, then sends a live message with the new unreadCount. It no longer also sends a push, which used to double every push. A missing type defaults to NOTIFICATION instead of silently dropping the inbox row.
Linking: each notification carries notificationType, entityType/entityId (e.g. PROFILE_GRANT, TENANT, CONVERSATION) and a data map with the ids a screen needs (agencyId, buildingId, tenantId…). This comes back in both the inbox and the live message.
Clear on action: answering a sharing request or an invitation, or reading a thread, marks its notifications read. PATCH /v1/notifications/read?entityType=&entityId= does the same on request.
Live badge: reading one, reading all, or clearing by entity sends an UNREAD_COUNT live event, so every open tab updates.
JSON names: the flags now come back as isRead and isStarred.
Channels:
Your admin sets them per topic in the existing policy screen.
User preferences apply only on topics where the admin allows it.
A new CHAT_MESSAGE topic (push by default) has been added.
V32 turns the topic columns into plain text, so future topics don't need a migration.
Async: @EnableAsync was missing, so the dispatcher's "async" sends ran on the request thread. They're asynchronous now.

Broadcasts land in each tenant's own thread, so replies stay private.
Channels start announcements-only. Staff can switch them to let tenants post.
Staff access uses TENANT_MESSAGE_READ / TENANT_MESSAGE_CREATE, which agency admins and caretakers already hold.
Live updates arrive as THREAD_MESSAGE events on the existing /user/queue/chat subscription.
Support chat is unchanged, but its queries now only see support conversations, so tenancy threads can't show up in the support queue or be claimed or closed from there.
Shop chat is left as a TODO.

I've removed the support desk and added shop conversations, so chat now covers agency communications and shop follow-ups. All 175 tests pass on a fresh run and the jar is rebuilt. Nothing is committed. Migrations V31–V33 will run on your next start.

Support desk removed: ChatController, including its /chat.* live handlers; TestChatController; ChatService/ChatServiceImpl; the typing indicators; and the unused support DTOs. Existing support rows stay in the database unused, so nothing fails to load.

Agency communications (unchanged from last round):

Tenancy threads: tenant ↔ agency staff.
Building channels: announcements-only by default, or open to tenants.
Broadcasts: to the whole agency, chosen buildings or chosen rooms, each landing in the tenant's own thread.
Shop conversations, either side can start one:

Who	Endpoint
Any user contacts the shop (general, or ?orderId= for one of their orders)	POST /v1/chat/threads/shop
Shop admin contacts a user (optionally about an order)	POST /v1/chat/threads/shop/customer/{userId}?orderId=
Shop admins' inbox (filter customerUserId, orderId)	GET /v1/chat/threads/shop
Who answers: users holding CHAT_ADMIN_READ/WRITE through a system role. ECOM_ADMIN already has both. Every shop admin sees and can answer every shop conversation, and all of them are notified of new customer messages.
One conversation per topic: each customer has one thread per order, plus one for general enquiries. Asking again reopens the same thread.
For the customer: shop threads appear in their GET /my list and count towards the chat unread badge. Messages, read state, live THREAD_MESSAGE events and notifications work the same as in agency threads, and the notification data includes orderId for linking.
