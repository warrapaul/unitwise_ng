//===================================== now review the landlord dashboard UI 
the following recommendations
the dashboard has a solid foundation for an agency administrator, but it needs improvements to its data presentation, operational priorities, and visual hierarchy before it is production-ready.

Compared with the tenant dashboard, this dashboard has a different purpose. A tenant needs to understand their own tenancy and payments. An AGENCY_ADMIN needs to understand the performance of the entire property portfolio, identify problems, and take action across multiple buildings, tenants, leases, and payments.

The current UI already has the right building blocks: rental collection, occupancy, tenant counts, lease status, building-level billing, arrears, and operational navigation. I would preserve those features while making the dashboard more actionable and fixing some important inconsistencies in the displayed figures.
1. What is already working well

Rental collection summary

Showing expected rent, collected rent, outstanding balances, and collection percentage gives the agency administrator a useful overview of financial performance.




Building-level operational table

The building table provides a practical way to compare room availability, occupancy, tenant numbers, arrears, billing status, and repairs across the portfolio.




Useful management metrics

Occupancy, tenants, leases, portfolio size, and move-ins and move-outs are relevant to an agency administrator's daily work.




A task-oriented sidebar

The navigation exposes important operational areas, including payments to confirm, overdue accounts, deposits, meter readings, rent adjustments, leases, and applications. These are valuable features for a property management platform.



The foundation is appropriate. The biggest opportunity is to turn the dashboard from a collection of statistics into a portfolio management and decision-making workspace.
2. Critical issues to address first

1. Fix metric formatting and data consistency
Critical
The building table appears to merge values such as 1 8% under Occupied and 6,00077% under Collected. These should be separate, clearly aligned values. The 77% collection rate itself is correct for KES 6,000 collected against KES 7,801 expected.

More importantly, the dashboard shows one active tenant, zero active leases, and one lease awaiting signature, while the building has one occupied room. This could be a legitimate workflow state, but the dashboard should make that relationship understandable rather than appearing contradictory.

Recommendation: Check the underlying metric definitions, table column sizing, and the relationship between occupancy, tenant status, and lease status.




2. Make “1 thing needs attention” useful

The alert bar is a good concept, but it does not identify the problem until the administrator expands it.

Recommendation: Show a short description, severity, and direct action. For example, “1 lease awaiting signature” with a Review lease action, if that is the outstanding task. If multiple types of issues exist, group them by urgency.




3. Reduce the oversized header

The header occupies a large portion of the initial viewport but contains little information. The large blank space between the navigation shortcuts and the rental collection card is not earning its space.

Recommendation: Make the header more compact. Place the page title, reporting period, relevant filters, and a small set of primary actions in a single, well-organized area.




4. Strengthen the financial overview

The collection card is useful, but the administrator cannot immediately tell whether 77% collection is good or poor for the current point in the month.

Recommendation: Add context such as the previous month's collection rate, change from the previous period, and the number of accounts overdue. Make sure comparisons use equivalent billing periods and clearly distinguish overdue arrears from amounts that are not yet due.




5. Make metrics actionable

The cards show counts, but the administrator needs to know which records make up those counts.

Recommendation: Let administrators click “Vacant,” “Awaiting signature,” “Outstanding,” and “Move-ins” to open filtered lists. Every important metric should lead to the relevant operational workflow.



3. Review of each dashboard section
A. Header and quick navigation
The current header says “Default overview” and shows an AGENCY_ADMIN badge. It is functional, but not particularly informative or polished.

Recommended changes:
- Replace “Default overview” with Agency overview or Portfolio overview.
- Show the agency name and reporting period where useful.
- Keep the AGENCY_ADMIN role as account metadata rather than a prominent page element.
- Replace the generic shortcut chips with meaningful primary actions, such as Add building, Add tenant, or Review payments, subject to permissions.
- Remove duplicate navigation links where the sidebar already provides the same destinations.
The shortcuts for Buildings, Tenants, Rent payments, and Arrears are useful, but should either be clearly presented as quick actions or omitted in favor of a more purposeful summary.
B. Rental collection summary

D. Occupancy
The current card shows one occupied room, 11 vacant rooms, zero reserved rooms, zero under maintenance, and an occupancy rate of 8.3%.

The calculations are consistent with 12 total rooms, but the card could be more informative.

Improvements:
- Make the occupancy rate the primary figure, with the occupied and available counts beneath it.
- Show reserved and under-maintenance rooms separately from available rooms.
- Provide a direct link to the vacant rooms list.
- Consider a small visual occupancy bar rather than relying only on numbers.
- If the portfolio grows, support filtering by building or comparing occupancy across properties.
An important business rule to define is whether rooms under maintenance count as vacant, unavailable, or a separate category. The same definition must be used throughout the dashboard.
E. Tenants
The current card shows one active tenant and zero awaiting verification or given notice. This is a useful summary, but it does not expose the actions an agency administrator may need to take.

Consider showing:
- Active tenants.
- Applications awaiting review.
- Tenants awaiting verification.
- Tenants who have given notice.
- Tenancies awaiting room assignment, if applicable.
Do not show every possible tenant status as a separate statistic. Show only the statuses that help the agency administrator take action, and let them open the relevant filtered tenant list.
F. Leases
The screenshot shows zero active leases, one lease awaiting signature, and zero leases expiring within 30 days.

The awaiting-signature count deserves more prominence because it represents a potential unfinished workflow.

Recommended changes:
- Highlight leases awaiting signature and link directly to those records.
- Show upcoming expirations over configurable periods, such as 30 and 60 days.
- Distinguish draft leases from leases awaiting the landlord's signature and leases awaiting the tenant's signature.
- Provide a clear lease lifecycle, from draft through signature to active tenancy.
- Ensure the occupancy and tenant summaries explain situations where a tenant occupies a room but the lease is not yet active.
A lease dashboard is most useful when it tells the administrator what needs attention, not just how many leases exist.
G. Portfolio
The portfolio card currently shows one building, 12 rooms, one active tenant, and zero active leases.

These are useful headline metrics. For an agency with multiple properties, I would add links to the building list and show a small amount of trend information where it helps decision-making.

For example, the administrator could compare the current room count with the previous period or see whether occupancy is improving. Avoid adding trend indicators unless historical data is available and the comparison is meaningful.
H. Moves in and out
This card shows one move-in, zero move-outs, zero transfers, and a net change of one.

The concept is useful, but the dashboard needs a clear period for these metrics. Otherwise, an administrator cannot tell whether the counts refer to today, this month, or the lifetime of the agency.

Recommendation: Add a reporting-period label and make each metric open a list of relevant tenancy events. The net change should be clearly defined as move-ins minus move-outs, with transfers treated according to the system's business rules.

4. What is missing from a production-ready landlord dashboard?
The current dashboard focuses mainly on rent collection and tenancy statistics. For an agency administrator managing multiple buildings, I would also make maintenance, operational tasks, and financial follow-up first-class parts of the experience.

1. Actionable tasks and approvals

Surface leases awaiting signature, tenant applications requiring review, payments awaiting confirmation, outstanding meter readings, and bills requiring approval. Every task should have an owner, status, and direct action where appropriate.




2. Maintenance and repairs overview

Show open repairs, urgent requests, overdue maintenance tasks, and unresolved issues by building. A count of zero is useful only if the system confirms that the count is current and includes all relevant requests.




3. Financial performance and reconciliation

In addition to rent collection, consider showing unallocated payments, payment reports awaiting confirmation, deposit liabilities, adjustments, and a link to financial reports. Keep actual cash received distinct from amounts reported by tenants but not yet confirmed.




4. Upcoming events

Highlight lease expirations, scheduled inspections, expected move-ins, and upcoming rent billing dates. Prioritize items that require action rather than filling the dashboard with a general calendar.




5. Portfolio-wide property context

As the agency grows, a compact property comparison or location view could help administrators identify low occupancy, high arrears, and maintenance hotspots. This can be introduced later, rather than adding a map simply for decoration.



I would not add all five as large dashboard cards. The dashboard should summarize them, with detailed workflows remaining in their dedicated sections.
5. Visual design and layout improvements
The existing visual style is consistent with the tenant dashboard: muted green accents, neutral backgrounds, rounded cards, and a left-hand navigation. I would preserve that design system.

The most noticeable issue is the use of space. The header is tall, the collection summary floats on the right, and the building table stretches across the page. The lower cards have a reasonable grid, but some contain only a few values and large amounts of unused space.









Compact the header

Reduce its vertical height, put the reporting period and key actions in a consistent toolbar, and use the recovered space for financial KPIs and actionable alerts.












Improve data density and alignment

Give numeric columns adequate width, right-align monetary amounts, prevent adjacent values from running together, and support horizontal scrolling or a responsive alternative on narrow screens.












Standardize KPI cards

Use consistent heading sizes, label placement, padding, and status treatments. Avoid giving every statistic equal emphasis; overdue balances and pending approvals deserve more attention than total portfolio size.












Test responsive layouts

At narrower widths, stack the KPI cards, allow the table to adapt, collapse the sidebar into a drawer, and keep the most important actions available without excessive scrolling.



I would also check keyboard navigation, focus indicators, text contrast, accessible labels, loading states, and empty states. A production dashboard should communicate when data is loading, when there is no data, and when data cannot be retrieved, rather than displaying misleading zeros.

7. Implementation priorities
Priority	What to address
P0 — Before release	Fix merged table values, verify metric definitions, reconcile occupancy with tenancy and lease statuses, and ensure financial figures and billing statuses are correct.
P1 — Dashboard UX	Compact the header, improve the collection summary, make the attention bar actionable, and add links from metrics to filtered records.
P2 — Operational improvements	Surface maintenance, lease expirations, pending approvals, and useful reporting-period comparisons.
P3 — Scale and polish	Add portfolio comparisons, richer trends, advanced filtering, and optional geographic visualizations when the agency has enough data to benefit.

One backend consideration is especially important: the dashboard should use consistent definitions for expected rent, collected rent, arrears, occupied rooms, active tenants, and active leases. The frontend should not independently derive those figures using different rules in different cards. Ideally, the API supplies a consistent summary for a specified reporting period, and the UI renders the summary alongside links to the underlying records.
Final verdict
I would retain the existing design system, but make the landlord dashboard more compact, more actionable, and more financially trustworthy.

The three changes I would prioritize above everything else are:
1. Fix the data presentation and validate the metrics. The merged table values and the apparent mismatch between occupied rooms, active tenants, and active leases undermine confidence.
2. Make the dashboard action-oriented. Pending signatures, overdue rent, unconfirmed payments, and maintenance issues should lead directly to the relevant records and workflows.
3. Reorganize the visual hierarchy. Give collection performance and outstanding tasks the strongest emphasis, reduce the oversized header, and make building-level information easier to scan.

D. Occupancy

- Provide a direct link to the vacant rooms list.
- Consider a small visual occupancy bar rather than relying only on numbers.

F. Leases
The screenshot shows zero active leases, one lease awaiting signature, and zero leases expiring within 30 days.

The awaiting-signature count deserves more prominence because it represents a potential unfinished workflow.

Recommended changes:
- Highlight leases awaiting signature and link directly to those records.
- Show upcoming expirations over configurable periods, such as 30 and 60 days.
- Distinguish draft leases from leases awaiting the landlord's signature and leases awaiting the tenant's signature.
- Provide a clear lease lifecycle, from draft through signature to active tenancy.
- Ensure the occupancy and tenant summaries explain situations where a tenant occupies a room but the lease is not yet active.
A lease dashboard is most useful when it tells the administrator what needs attention, not just how many leases exist.
G. Portfolio
The portfolio card currently shows one building, 12 rooms, one active tenant, and zero active leases.

These are useful headline metrics. For an agency with multiple properties, I would add links to the building list and show a small amount of trend information where it helps decision-making.

For example, the administrator could compare the current room count with the previous period or see whether occupancy is improving. Avoid adding trend indicators unless historical data is available and the comparison is meaningful.
H. Moves in and out
This card shows one move-in, zero move-outs, zero transfers, and a net change of one.

The concept is useful, but the dashboard needs a clear period for these metrics. Otherwise, an administrator cannot tell whether the counts refer to today, this month, or the lifetime of the agency.

Recommendation: Add a reporting-period label and make each metric open a list of relevant tenancy events. The net change should be clearly defined as move-ins minus move-outs, with transfers treated according to the system's business rules.

4. What is missing from a production-ready landlord dashboard?
The current dashboard focuses mainly on rent collection and tenancy statistics. For an agency administrator managing multiple buildings, I would also make maintenance, operational tasks, and financial follow-up first-class parts of the experience.

1. Actionable tasks and approvals

Surface leases awaiting signature, tenant applications requiring review, payments awaiting confirmation, outstanding meter readings, and bills requiring approval. Every task should have an owner, status, and direct action where appropriate.




2. Maintenance and repairs overview

Show open repairs, urgent requests, overdue maintenance tasks, and unresolved issues by building. A count of zero is useful only if the system confirms that the count is current and includes all relevant requests.




3. Financial performance and reconciliation

In addition to rent collection, consider showing unallocated payments, payment reports awaiting confirmation, deposit liabilities, adjustments, and a link to financial reports. Keep actual cash received distinct from amounts reported by tenants but not yet confirmed.




4. Upcoming events

Highlight lease expirations, scheduled inspections, expected move-ins, and upcoming rent billing dates. Prioritize items that require action rather than filling the dashboard with a general calendar.




5. Portfolio-wide property context

As the agency grows, a compact property comparison or location view could help administrators identify low occupancy, high arrears, and maintenance hotspots. This can be introduced later, rather than adding a map simply for decoration.



I would not add all five as large dashboard cards. The dashboard should summarize them, with detailed workflows remaining in their dedicated sections.
5. Visual design and layout improvements
The existing visual style is consistent with the tenant dashboard: muted green accents, neutral backgrounds, rounded cards, and a left-hand navigation. I would preserve that design system.

The most noticeable issue is the use of space. The header is tall, the collection summary floats on the right, and the building table stretches across the page. The lower cards have a reasonable grid, but some contain only a few values and large amounts of unused space.









Compact the header

Reduce its vertical height, put the reporting period and key actions in a consistent toolbar, and use the recovered space for financial KPIs and actionable alerts.












Improve data density and alignment

Give numeric columns adequate width, right-align monetary amounts, prevent adjacent values from running together, and support horizontal scrolling or a responsive alternative on narrow screens.












Standardize KPI cards

Use consistent heading sizes, label placement, padding, and status treatments. Avoid giving every statistic equal emphasis; overdue balances and pending approvals deserve more attention than total portfolio size.












Test responsive layouts

At narrower widths, stack the KPI cards, allow the table to adapt, collapse the sidebar into a drawer, and keep the most important actions available without excessive scrolling.



I would also check keyboard navigation, focus indicators, text contrast, accessible labels, loading states, and empty states. A production dashboard should communicate when data is loading, when there is no data, and when data cannot be retrieved, rather than displaying misleading zeros.

7. Implementation priorities
Priority	What to address
P0 — Before release	Fix merged table values, verify metric definitions, reconcile occupancy with tenancy and lease statuses, and ensure financial figures and billing statuses are correct.
P1 — Dashboard UX	Compact the header, improve the collection summary, make the attention bar actionable, and add links from metrics to filtered records.
P2 — Operational improvements	Surface maintenance, lease expirations, pending approvals, and useful reporting-period comparisons.
P3 — Scale and polish	Add portfolio comparisons, richer trends, advanced filtering, and optional geographic visualizations when the agency has enough data to benefit.

One backend consideration is especially important: the dashboard should use consistent definitions for expected rent, collected rent, arrears, occupied rooms, active tenants, and active leases. The frontend should not independently derive those figures using different rules in different cards. Ideally, the API supplies a consistent summary for a specified reporting period, and the UI renders the summary alongside links to the underlying records.
Final verdict
I would retain the existing design system, but make the landlord dashboard more compact, more actionable, and more financially trustworthy.

The three changes I would prioritize above everything else are:
1. Fix the data presentation and validate the metrics. The merged table values and the apparent mismatch between occupied rooms, active tenants, and active leases undermine confidence.
2. Make the dashboard action-oriented. Pending signatures, overdue rent, unconfirmed payments, and maintenance issues should lead directly to the relevant records and workflows.
3. Reorganize the visual hierarchy. Give collection performance and outstanding tasks the strongest emphasis, reduce the oversized header, and make building-level information easier to scan.
